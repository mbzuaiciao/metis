## Revised submission and outcome policy

One explicit `--execute` invocation makes **one intentional `spawn` submission**, with `retries=0`, no local resubmission loop, one L40S and the existing one-step/840-second bounds per execution. A FunctionCall handle is used only to retain its ID, wait once for a result and request cleanup inside an ephemeral `app.run()` context. It is not detached/deployed work. The new private output directory is exclusive; attempting the same output path again fails before submission. A lost submission acknowledgement remains unknown and is never repaired by another submit.

The launcher writes an INCONCLUSIVE manifest before cloud work and before submission. It records a unique submission UUID, intent/acknowledgement state, UTC timestamps, app/function/call IDs and timings. The runtime records a fresh execution UUID, PID, UTC startup/end, documented input/call IDs, container ID (`MODAL_TASK_ID`), image, region and cloud. Only an explicit allowlist is read; identity tokens or the full environment are never recorded. Structured start/interruption/finish events reach platform logs where delivery succeeds. No new persistent ledger, volume or service is introduced.

The launcher obtains one public call-graph snapshot before waiting and one after return/failure. It records input/container assignments and terminal statuses. Multiple container assignments for the same logical call are reported as an observed restart **or reassignment**, not an authenticated physical-attempt count. Signal interruption, watchdog exit, exception, timeout, missing/malformed result, mismatched identity, failed cleanup or missing graph data makes the result **INCONCLUSIVE**. Cancellation requests `terminate_containers=True` in `finally`, and the ephemeral app context exits; cleanup acknowledgement is recorded rather than asserted as a measured GPU shutdown time. A killed local process may leave the initial INCONCLUSIVE record and incomplete cleanup evidence.

**No overall PASS can be established with the current public history API.** Modal explicitly documents `get_call_graph()` as best effort, delayed and potentially truncated; the IDs and a successful result do not prove all physical attempts were observed. Accordingly `physical_history_complete=false` is fixed by the implementation, and even a normal-looking successful return has overall `status=INCONCLUSIVE`. `technical_status=passed` separately means the returned execution completed the retained technical checks. It is useful compatibility evidence about that execution, not an uninterrupted-run PASS or proof of exactly-once execution. No manual history-complete override is supplied. A prior attempt that died before startup telemetry may remain invisible. No observed restart means only that none was observed.

A plan or successful offline check does not authorize launch. The original strict physical-attempt blocker is removed by the user's policy amendment; runtime uncertainty is now expressed in the result rather than used to block submission. Per-attempt one-step and time limits cannot guarantee a one-step aggregate across hidden physical replays, an aggregate 15-minute GPU limit or a maximum bill. Infrastructure replacements may repeat work. A 900-second local result wait followed by cancellation limits intentional waiting but is not a provider billing guarantee; SDK RPC/startup/teardown and cancellation failures can add time. No auto-resubmission follows any exit status.

Sources reviewed 2026-11-01: [FunctionCall graph/get/cancel APIs](https://modal.com/docs/reference/modal.FunctionCall), [InputInfo fields](https://modal.com/docs/sdk/py/latest/types), [runtime environment IDs](https://modal.com/docs/guide/environment_variables), [preemption](https://modal.com/docs/guide/preemption) and [per-attempt timeouts](https://modal.com/docs/guide/timeouts). The pinned client's local definition/output API is checked offline; remote initialization and telemetry remain untested and fail conservatively. No GPU execution occurred.
