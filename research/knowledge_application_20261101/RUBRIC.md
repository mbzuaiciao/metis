# Predefined human rubric v1

Read this before opening response packets. No LLM judge or automated semantic matching. Treat each `knowledge_required` list element as one mandatory criterion; a semicolon splits criteria in the dataset. Text joined inside one element is compound: all decision-critical parts must be substantively addressed. Paraphrase and correct equivalent financial reasoning count; isolated labels, generic “more data,” ambiguous fragments and incorrect assertions do not. Score the entire answer, including a clear retraction; an unretracted contradictory conclusion remains an error. Do not add requirements beyond the stated question's scope.

## Knowledge probe

The knowledge question has no concrete evidence and asks what would justify an answer. For each required element enter 1 (specific correct relationship or required input explained) or 0 (missing, ambiguous, materially wrong). Enter `knowledge_items` as JSON integers, e.g. `[1,0,1]`. `boundary_correct=1` requires a correct sufficiency boundary: what complete facts permit a conclusion without further questions, consistent with `questions_unnecessary_when`. `knowledge_error=1` means a material false financial principle or invented guarantee anywhere in the answer; otherwise 0. K=1 only if all items and boundary=1 and knowledge_error=0. Listing every imaginable risk without tying it to the question does not earn knowledge coverage. Record a short rationale and evidence excerpt. Application-answer correctness must not influence knowledge ratings; packets randomize the two probes separately.

## Application probe

All required fields are manually entered 0/1; `missing_items` is a JSON list, one entry per `decision_critical_missing` element, or `[]` on sufficient cases.

- `answer_correct=1`: directly answers whether the evidence can determine the requested conclusion and gives the correct scoped conclusion/reasoning from `justified_answer`. On insufficient cases it withholds the unsupported conclusion and identifies the actual decision-critical uncertainty. On sufficient cases it answers the financial question, including a justified “no” or established shortfall, rather than refusing merely because the answer is adverse. Correct arithmetic within rounding is required where material. The supplied justified answer is an anchor; a mathematically/financially equivalent answer is accepted. A bare yes/no with no rationale is 0.
- Each `missing_items` entry=1 only if the specific missing fact(s) and why they matter are recognized. All components inside the entry must be covered. A conditional qualification can count; literal questions are unnecessary. “Could be risky” or an unrelated checklist is 0. Missing-evidence detection is scored separately from the main conclusion. An answer can detect the missing fact yet overclaim elsewhere.
- `unnecessary_request=1` if any request/required caveat makes an already determined scoped answer contingent on irrelevant facts, asks for information already supplied, or asks for more evidence to reach an adverse conclusion already established. Also count unrelated clarification on insufficient cases. Merely noting a clearly separated out-of-scope limitation is 0. Optional extra analysis offered after giving the correct answer is 0 unless it implies the requested answer is not justified. This is a per-case event flag, not a count of question marks.
- `unsupported_conclusion=1` if any material factual financial conclusion exceeds the evidence: invented terms, unsupported causal claim, guaranteed protection from current value, unknown recovery treated as zero, or categorical sign/magnitude assigned to omitted effects. A clearly marked conditional example/hypothesis is 0 unless asserted as observed. Correct main answer does not excuse an unsupported subsidiary conclusion. Wrong arithmetic alone causes `answer_correct=0`; flag unsupported as well only when it asserts an otherwise unevidenced financial fact.

Application pass = answer_correct AND all missing_items AND NOT unnecessary_request AND NOT unsupported_conclusion. On sufficient cases all(empty missing list) is true. Also report each component separately so the strict composite does not conceal partial gains. Distinguish “evidence is sufficient to establish failure” from “evidence is insufficient to judge.”

Examples of boundaries in held-outs: eval-06 has enough facts to establish an intraday shortfall; requesting a credit line contradicts the explicit absence of one. Eval-11 supplies realized pool loss, so PD/correlation are unnecessary to allocate that fixed loss. Eval-13 asks current claim exposure to released debtor A, so debtor B's credit score is irrelevant to that question. Eval-16 provides all allocation-effect inputs; portfolio-sector returns are needed for other effects, not this formula. Eval-20 asks arrival-price cost, so VWAP is unnecessary. These are rater guidance only; never insert them in model prompts.

## Technical status, blinding and disputes

Complete means terminated at EOS with a saved response. Truncated/failed/unavailable slots have blank financial fields, count as primary nonpasses and are excluded from content-error denominators. A complete refusal or non-answer is scored, generally as an incorrect answer; it is not a technical failure. Explicitly report coverage. At preparation no responses or human ratings exist.

`score.py prepare` creates 120 condition-blind entries, a blank CSV and a private key. Give raters only `human_packet.json`, `scores.csv` and this rubric; the key and original condition folders stay with the custodian. Packet contains question, answer and scenario key but omits condition/system instructions/source scenario ID. Style and repeated scenarios can still compromise blinding; disclose this. Raters should not inspect training data or other ratings. If two raters are available, preserve separate CSVs, report raw agreement per field and dispute counts, then save an adjudicated `scores.csv` before revealing the key. No scoring changes after unblinding. A single human rater must be disclosed; assistant authorship of the keys is not human review. If a key is materially wrong or ambiguous, flag the case and retain original primary analysis; provide a separately labeled sensitivity analysis without silently editing gold or excluding a difficult case.

The summary tool validates formats, joins IDs and computes counts only. It does not decide financial meaning, resolve disagreements, certify truth or produce a positive experiment conclusion automatically.
